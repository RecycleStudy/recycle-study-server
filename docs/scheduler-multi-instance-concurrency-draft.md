# 서론

## 서비스 소개

RecycleStudy 서비스는 복습하고 싶은 URL 링크를 저장하면 주기적으로 복습 내용을 이메일로 전송해주는 서비스입니다. 사용자가 직접 복습 주기를 커스텀하여 원하는 주기와 시간대에 이메일을 받을 수 있는 기능을 제공하고 있습니다.

## 문제를 인식한 계기

이 문제는 이메일 스케줄러 성능 테스트를 마친 직후 다음 단계로 식별하였습니다. 인스턴스를 2개 이상으로 늘릴 경우 현재 스케줄러 구조에 동시성 문제가 있다는 것을 발견하였습니다.

현재 구조는 단일 인스턴스를 암묵적으로 가정합니다. 다중 인스턴스로 배포하면 모든 인스턴스가 동일한 스케줄러를 실행하므로 같은 이메일이 중복 발송될 수 있습니다. "수평 확장이 가능한 구조인가?"를 검토하면서 이 문제를 정의하게 되었습니다.

---

# 1. 문제 인식

## 1-1. 구체적인 경쟁 조건 시나리오

두 인스턴스가 동시에 스케줄러를 실행하면 다음과 같은 순서로 중복 발송이 발생합니다.

```
인스턴스 A: findAllByScheduledAt() → cycleA (PENDING) 조회
인스턴스 B: findAllByScheduledAt() → cycleA (PENDING) 조회  ← 동시
→ A: cycleA 이메일 발송
→ B: cycleA 이메일 발송
→ 사용자에게 동일한 복습 이메일 2통 수신
```

핵심은 SELECT와 `UPDATE status = SENT` 사이의 타임 윈도우입니다. A가 PENDING을 조회한 뒤 SENT로 갱신하기 전에 B가 동일한 행을 조회하면 두 인스턴스 모두 발송을 진행합니다.

## 1-2. 왜 현재 구조에서 발생하는가

현재 발송 흐름은 다음과 같이 두 트랜잭션으로 분리되어 있습니다.

```
ReviewEmailSender (@Scheduled, cron)
  └─ reviewCycleService.findTargetReviewCycle()    @Transactional(readOnly)  ← T1
       └─ findAllByScheduledAt(scheduledAt, PENDING)
  └─ singleReviewEmailSender.sendOne()             @Async (VT)               ← T2 (별도 스레드)
       └─ notificationHistoryService.updateStatus() @Transactional
```

T1(`findTargetReviewCycle`)은 읽기 전용 트랜잭션으로, 메서드가 반환되는 시점에 트랜잭션이 종료됩니다. T2(`sendOne`)는 `@Async`로 별도 스레드에서 실행되므로 T1과 독립적인 트랜잭션을 사용합니다.

결과적으로 T1이 반환된 뒤 T2가 `UPDATE status = SENT`를 실행하기까지 타임 윈도우가 열려 있습니다. 이 사이에 다른 인스턴스의 T1이 동일한 행을 조회할 수 있습니다.

# 2. 도메인 특성 분석

해결 방법을 선택하기 전에 이 서비스의 조건을 먼저 정립하였습니다. 조건이 명확해야 여러 후보 중 어느 것이 적합한지를 수치에서 역산할 수 있기 때문입니다.

## 2-1. 발송 볼륨과 스파이크 특성

이 내용은 성능 테스트 문서에서 도출된 수치를 직접 인용합니다.

스케줄러의 최대 부하는 모든 사용자의 `notification_time`이 같은 분에 집중될 때 발생합니다.

```
DAU 500명, 전원 notification_time = 20:00 설정 시:

20:00 스케줄러 실행:
  - 어제의 1일 복습 + 7일 전의 7일 복습 + 30일 전의 30일 복습
  - 500명 × 1건(같은 scheduledAt으로 그룹핑) = 500건의 이메일을 1분 내에 발송해야 함

단기 복습(10분, 1시간)은 18:00~24:00에 분산:
  - 500명 × 4건 / 360분 ≈ 5.6건/분
```

| 시나리오 | 건수/분 |
|---------|-------|
| notification_time 스파이크 (DAU 500, 전원 같은 시각) | 500건/분 |
| 단기 복습(10분, 1시간) 분산 | ~6건/분 |

두 시나리오의 볼륨 차이가 80배 이상입니다. 이 서비스에서 의미 있는 부하 시나리오는 분산 처리가 아니라 스파이크 처리이며, 동시성 문제도 스파이크 상황에서 가장 빈번하게 발생합니다.

## 2-2. 중복 발송의 허용 수준

중복 발송에 대한 서비스의 허용 수준을 정의하는 것이 해결 방법 선택의 첫 번째 분기점입니다.

| 항목 | 이 서비스의 특성 |
|------|-------------|
| 이메일 성격 | 복습 알림 (결제·인증·OTP 아님) |
| 중복 발송의 영향 | "불편"하지만 "치명적"이지 않음 |
| 중복 발송 빈도 | 다중 인스턴스 배포 중 재배포 타이밍에만 발생 |
| 허용 수준 | at-least-once 허용 가능 |

결제나 인증 이메일이라면 exactly-once를 보장해야 하므로 발송 자체의 멱등성이 필수입니다. 복습 알림은 중복 수신이 허용 가능한 수준의 불편으로, 락으로 동시 실행을 막는 것만으로도 충분합니다.

이 판단이 후보군을 좁히는 첫 번째 기준입니다. 발송 멱등성이 필수라면 DB 상태 기반 접근이 요구사항이 됩니다. at-least-once로 충분하다면 실행 단위에 락을 걸어 중복 실행을 방지하는 방식도 선택지가 됩니다.

## 2-3. 인프라 제약

| 구성 요소 | 스펙 | 비고 |
|----------|------|------|
| Spring 서버 | t4g.micro (2 vCPU, 1GB RAM), Docker | 다중 인스턴스 배포 대상 |
| MySQL | t4g.micro (2 vCPU, 1GB RAM) | 이미 운영 중 |
| Redis | 없음 | 추가 인프라 도입 비용 발생 |
| 목표 DAU | ~500명 | AWS SES 무료 한도에서 역산 |

Redis가 없고, 목표 규모(DAU ~500)는 아키텍처를 전면 변경해야 할 규모가 아닙니다. 인프라 단순성을 유지하는 것이 이 서비스 규모에서 적절합니다.

이 제약이 후보군을 좁히는 두 번째 기준입니다. Redis 없이 적용 가능한 방법으로 범위를 한정할 수 있습니다.

## 2-4. 현재 아키텍처 트랜잭션 구조 (복선)

2-3의 제약을 확인한 뒤 남은 후보들을 현재 코드 구조와 대조하면 예상치 못한 호환성 문제가 드러납니다.

```
T1: findTargetReviewCycle()   @Transactional(readOnly) → 반환 시 트랜잭션/잠금 해제
T2: sendOne()                 @Async (VT), 별도 트랜잭션
```

T1이 종료되는 시점에 T1이 획득한 모든 DB 잠금이 해제됩니다. T2는 그 이후에 독립적으로 실행됩니다. 이 구조가 특정 방법과 어떻게 충돌하는지는 4장에서 구체적으로 전개합니다.

# 3. 해결 방법 후보 도출

2장의 분석에서 두 후보를 먼저 탈락시킬 수 있습니다.

- **Redis 분산 락 (Redisson / SETNX)**: 2-3에서 Redis가 없음. 도입 시 인프라 운영 비용 증가. DAU ~500 규모에 비해 비용 대비 효과가 낮음 → 제외
- **메시지 큐 (SQS / RabbitMQ)**: 큐 서버 추가와 아키텍처 전면 변경이 필요. DAU ~500 규모에 과함 → 제외

남은 3개 후보를 상세 분석합니다.

## 3-1. ShedLock (DB 기반 분산 락)

**메커니즘**

```
인스턴스 A: shedlock 테이블에 락 레코드 INSERT → 성공 → 스케줄러 실행
인스턴스 B: shedlock 테이블에 락 레코드 INSERT → 실패 → 해당 틱 스킵
```

한 인스턴스만 스케줄러를 실행하도록 보장합니다. 스케줄러 자체의 중복 실행을 막는 방식이므로 발송 로직에 변경이 없습니다.

**변경 범위**

- `build.gradle`: `shedlock-spring`, `shedlock-provider-jdbc-template` 의존성 추가
- `ReviewEmailSender`, `EmailRetryScheduler`: `@SchedulerLock` 애노테이션 추가
- DB 마이그레이션: `shedlock` 테이블 DDL 추가

**트레이드오프**

| 항목 | 내용 |
|------|------|
| 인프라 추가 | 없음 (MySQL 사용) |
| 구현 복잡도 | 낮음 |
| 현 아키텍처 호환 | 완전 호환 (발송 로직 무변경) |
| 보장 수준 | 한 인스턴스만 실행 (at-least-once) |
| 한계 | 락 획득 실패 인스턴스는 해당 틱 완전 스킵 → 최대 1분 발송 지연 가능 |

## 3-2. DB 상태 기반 멱등성 (PROCESSING 상태 전이)

**메커니즘**

```sql
-- 조회 전 원자적 상태 전이
UPDATE notification_history SET status = 'PROCESSING'
WHERE status = 'PENDING' AND scheduled_at <= :now
-- UPDATE 성공 건수만큼만 발송 진행
```

MySQL의 행 단위 잠금 덕분에 두 인스턴스가 동시에 실행해도 각자 다른 행만 처리합니다. `UPDATE`가 원자적으로 실행되므로 같은 행을 두 인스턴스가 동시에 PROCESSING으로 전환하는 것이 불가능합니다.

**변경 범위**

- `NotificationStatus` enum: `PROCESSING` 추가
- `NotificationHistoryRepository`: 상태 전이 쿼리 추가
- `ReviewEmailSender`: PENDING 조회 방식 → PROCESSING 전환 후 처리로 재설계
- 추가 필요: stuck PROCESSING 레코드 처리 스케줄러 (타임아웃 후 FAILED 전환)

**트레이드오프**

| 항목 | 내용 |
|------|------|
| 인프라 추가 | 없음 |
| 구현 복잡도 | 높음 (PROCESSING stuck 처리 로직 포함) |
| 현 아키텍처 호환 | 트랜잭션 구조 재설계 필요 |
| 보장 수준 | 발송 자체 멱등성 보장 (DB 원자적 UPDATE) |
| 한계 | stuck 레코드 처리 로직이 없으면 발송 영구 중단 가능 |

## 3-3. FOR UPDATE SKIP LOCKED (DB 비관적 잠금)

**메커니즘**

MySQL 8.0+에서 지원. 이미 다른 트랜잭션이 잠금 중인 행을 대기 없이 결과에서 제외합니다.

```sql
SELECT id, review_cycle_id
FROM notification_history
WHERE status = 'PENDING' AND scheduled_at <= :now
FOR UPDATE SKIP LOCKED
```

인스턴스 A가 행 X를 잠금 중이면 인스턴스 B의 동일 쿼리 결과에서 행 X가 제외됩니다. 여러 인스턴스가 서로 다른 행을 병렬로 처리할 수 있는 구조입니다.

이 방법에는 현재 아키텍처와의 호환성 문제가 있습니다. 4장에서 상세히 분석합니다.

# 4. 비교 분석

## 4-1. SKIP LOCKED의 현재 아키텍처와의 충돌

SKIP LOCKED는 직관적으로 이 문제를 해결하는 방법처럼 보입니다. 그러나 현재 코드 구조와 대조하면 예상대로 동작하지 않습니다.

**예상 동작**

```
인스턴스 A: FOR UPDATE SKIP LOCKED → 행 X 잠금 획득
인스턴스 B: FOR UPDATE SKIP LOCKED → 행 X skip → 중복 발송 없음
```

**실제 동작 (현재 아키텍처)**

```
T1: findTargetReviewCycle()  @Transactional(readOnly) → 반환 시 트랜잭션 커밋 → 잠금 해제
    (FOR UPDATE SKIP LOCKED로 획득한 잠금이 이 시점에 해제됨)
T2: sendOne()                @Async (VT), 별도 트랜잭션

인스턴스 A의 T1이 반환된 뒤 → 행 X의 잠금 해제
→ 인스턴스 B의 T1이 행 X를 조회 가능 → 중복 발송 발생
→ SKIP LOCKED가 있어도 경쟁 조건 미해소
```

SKIP LOCKED로 획득한 잠금은 해당 트랜잭션이 커밋 또는 롤백될 때 해제됩니다. T1은 읽기 전용 트랜잭션이므로 메서드 반환 시 커밋되어 잠금이 풀립니다. T2(`sendOne`)는 별도 `@Async` 스레드에서 실행되므로 T1의 잠금과 아무 관련이 없습니다.

**올바른 적용 패턴**

SKIP LOCKED가 의미 있으려면 SELECT와 상태 전이를 같은 트랜잭션으로 묶어야 합니다.

```
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED  ← 행 잠금 획득 + 다른 인스턴스 skip
  UPDATE status = 'PROCESSING' WHERE id IN (:ids)
COMMIT                                ← 잠금 해제, 이미 PROCESSING → 재조회해도 안전
이후 비동기 발송
```

이 패턴은 사실상 3-2(PROCESSING 상태 전이)와 동일한 결과를 낳습니다. MySQL의 `UPDATE WHERE status = PENDING`만으로도 행 잠금으로 동일한 원자성을 보장할 수 있으므로, SKIP LOCKED를 추가해도 실질적인 안전성 향상은 크지 않습니다. 그리고 JPQL이 `FOR UPDATE SKIP LOCKED`를 지원하지 않아 native query가 필요합니다.

이 분석의 핵심은 단순히 "SKIP LOCKED는 현 구조에 안 맞다"가 아닙니다. SELECT와 UPDATE 사이의 잠금 경계가 트랜잭션 경계와 일치해야 한다는 것, 그리고 `@Async` 분리 패턴이 잠금 범위를 암묵적으로 좁힌다는 점입니다. 코드베이스에서 `@Transactional(readOnly)`와 `@Async`를 자연스럽게 조합할 때 이런 트랜잭션 경계 문제가 숨어 있을 수 있습니다.

## 4-2. 3개 후보 비교

| 항목 | ShedLock | PROCESSING 전이 | SKIP LOCKED |
|------|---------|----------------|------------|
| 중복 발송 방지 | 락으로 실행 자체를 막음 | DB 원자성으로 방지 | PROCESSING 전이와 동일 |
| **현 아키텍처 호환** | **완전 호환** | 트랜잭션 재설계 필요 | **현 구조에서 경쟁 조건 미해소** |
| 구현 복잡도 | 낮음 | 높음 (stuck 처리 포함) | 높음 (native query + 트랜잭션 재설계) |
| 인프라 추가 | 없음 | 없음 | 없음 (MySQL 8.0+ 필요) |
| 발송 멱등성 | 없음 (락으로만 보호) | 있음 | 있음 (PROCESSING 결합 시) |
| at-least-once로 충분할 때 | 적합 | 과함 | 과함 |
| stuck 처리 필요 | 없음 | 있음 | 있음 |
| 1분 지연 가능성 | 있음 (틱 스킵) | 없음 | 없음 |

## ShedLock 선택 시 근거 구조

**선택: ShedLock**

도메인 분석에서 역산하면 ShedLock이 현재 서비스에 적합합니다.

- 2-2에서 이 서비스의 이메일은 복습 알림이며 at-least-once를 허용합니다. 발송 멱등성이 비즈니스 요구사항이 아니므로 락으로 동시 실행만 막아도 충분합니다. PROCESSING 전이와 같은 복잡한 멱등성 보장은 이 서비스의 요구사항을 초과합니다.
- 2-3에서 MySQL을 이미 운영 중이므로 shedlock 테이블 하나만 추가하면 인프라 변경 없이 적용됩니다.
- 4-2에서 현재 아키텍처와 완전히 호환되어 발송 로직을 변경할 필요가 없습니다.

틱 스킵으로 인한 최대 1분 발송 지연은 이 서비스의 특성(복습 알림, 분 단위 지연 허용 가능)에서 허용 가능한 트레이드오프입니다.

**단계별 적용 계획**

| 단계 | 조건 | 변경 사항 |
|-----|------|---------|
| 현재 | 단일 인스턴스 | 변경 없음 |
| 수평 확장 시 | 다중 인스턴스 배포 | ShedLock 적용 (의존성 추가 + shedlock 테이블 + `@SchedulerLock`) |
| 향후 멱등성 요구 시 | 비즈니스 요건 변경 | PROCESSING 전이로 전환 |

---

## PROCESSING 전이 선택 시 근거 구조

**선택: PROCESSING 상태 전이**

- 향후 규모 확대 또는 발송 멱등성이 비즈니스 요건이 되는 시점을 선제적으로 대응합니다.
- 인스턴스 간 부하 분산: ShedLock은 한 인스턴스만 발송을 수행하지만 PROCESSING 전이는 모든 인스턴스가 서로 다른 행을 처리할 수 있어 처리량이 수평 확장에 비례합니다.
- 트랜잭션 재설계와 stuck 처리 로직이라는 구현 복잡도를 감수하는 trade-off가 있습니다.

---

## 이 과정에서 얻은 교훈

- **도메인 특성이 선택을 좁힌다.** 5가지 방법을 나열하는 것에서 시작했지만 중복 발송 허용 수준(2-2)과 인프라 제약(2-3)을 정의하는 것만으로 후보가 2개로 좁혀졌습니다. 기술 선택은 기술 문제가 아니라 도메인 제약 문제입니다.

- **트랜잭션 경계가 잠금 범위를 결정한다.** SKIP LOCKED가 현재 구조에서 동작하지 않는 이유는 `@Transactional(readOnly)`와 `@Async`의 조합이 잠금 범위를 암묵적으로 좁히기 때문입니다. "SKIP LOCKED를 쓰면 안전하다"는 직관은 잠금이 트랜잭션 종료까지만 유효하다는 전제 위에서만 성립합니다. 비동기 분리 패턴에서 이 전제가 무너집니다.

- **탈락 후보도 분석한다.** SKIP LOCKED를 제외 목록에 1문장으로 쓰는 대신 왜 현재 구조와 충돌하는지를 분석했습니다. 이 분석 과정에서 현재 아키텍처의 트랜잭션 경계에 대한 이해가 깊어졌고, PROCESSING 전이를 적용할 때 트랜잭션 구조를 어떻게 재설계해야 하는지를 구체화할 수 있었습니다.
